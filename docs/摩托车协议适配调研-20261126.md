## 凯越625X关键流程

- 手机加入仪表Wi-Fi；上游默认TCP目标192.168.4.1:8200，实际实现要允许现场地址核对。
- 四个FE同步字节及命令/长度/校验构成控制帧；尺寸查询B0 + 01 00 01。
- 使用地图显示模式A0{6}并处理确认与重发；该模式传输的是整张画面，不只是转向箭头。上游另有镜像模式B0/A0{7}，不能混用而忽略模式确认。
- JPEG封包使用40字节头、32字节对齐、类型0、帧ID、长度及校验；上游625X报告H264未得到有效确认，不能直接发送现有H264就认为可用。
- 发送窗口为2，按ACK限流、只保留最新待发帧，避免积压导致画面延迟。退出和重新连接需清空会话状态；ACK与超时应独立处理，不能套用PXC保活。
- 640×480和约7–8FPS来自上游特定车辆/手机报告，不是CarWithin性能承诺；尺寸以仪表回复为准。

建议数据链：现有本机CarPlay H264 → 解码CVPixelBuffer → 按仪表协商尺寸缩放 → JPEG → Yunmo封装 → TCP → 仪表ACK。可参考现有TailingOutput的图像处理，但独立新增YunmoOutput/YunmoConnection，不改极核6.2或春风状态机。

## 实施边界与建议顺序

1. 保持当前手机测试包，收集九号、热点、春风故障车及新增AE6结果；旧极核6.2已收到本轮通过反馈。
2. 有625X测试者时优先独立实现Yunmo最小闭环：连网、尺寸、模式、首帧、ACK、停止与重连，再验证完整CarPlay画面和延迟。
3. EasyConn先做通用仪表发现及协商尺寸，再由有设备的车主逐个验证；不同固件的身份、心跳和ACK差异只按配置启用。
4. ThinkerRide排后，需BLE配对和投屏状态实车验证。车把控制、触控回传分别验收，不能由出画结果推导。

本轮没有新增应用代码、没有宣称新增车型已支持、没有发布。

## 用户授权后的本地移植

用户要求按车型或仪表方案继续追加 Profile。候选目录 `/tmp/carwithin-motorcycle-port-20261126` 从当前开发源码快照建立，保留已有未发布的 #45/#48/#57 及春风/AE6 修复；未从公开 main 覆盖本地源码。

- 新增 13 个 Profile：春风 700MT-ADV、800MT、675SRR；贝纳利 TRK502/702/702X 分组；无极 DS800X；升仕 368E、368G、703RR；钱江 SRT550；凯越 625X；摩托莫里尼 X-Cape1200；凯越 450 Rally、800X。菜单均标记待实测，原有编号 0–11 保留，新项从 12 追加。
- EasyConn 族使用独立输出实例，复用 PXC 基础并新增受 Profile 控制的 mDNS 发现，获取 IPv4、端口和 package 后执行完整 EC 握手。无 mDNS 时尝试手动地址或网关 .1 的 10930 完整握手。原有春风预设关闭该发现开关，保留旧启动路径；未实现 Android Wi-Fi Direct 配网。
- Yunmo 独立实现尺寸查询、模式确认、JPEG 封包、ACK 窗口 2、窗口释放后采样最新画面、超时、退出和停止唤醒。仅接入 JPEG 路径；没有把默认尺寸当作成功协商。
- ThinkerRide 独立实现扫描及用户选择 BLE、服务与通知发现、分片 JSON、配对确认、写入背压及间隔、BLE 保活、投屏启停；450 使用 byteCat，800X 使用裸 JSON。TCP 监听 17818/15457/15456，包含控制握手、激活状态检查、心跳、视频尺寸头和 H.264 发送。未实现车把控制、触控回传或激活绕过。
- IP 与显式选择的 BLE UUID 按 Profile 分别保存，不自动连接扫描到的第一辆车。蓝牙长度不足或配对未确认会明确失败。

## 凯越625X首次用户日志反馈

用户提供测试者16:58–17:02的日志。MFi资源加载及ECDSA自检成功，iOS配件认证/识别通过，但本机请求192.168.4.2:7000后没有收到CarPlay控制TCP连接；0x4301多次重试仍未回连。不能把MFi通过当作CarPlay视频已经建立，也不能据此断定Wi-Fi密码一定错误。需要先确认测试者手机预览是否黑屏，Wi-Fi预设是否与实际仪表热点完全一致，再用相同Wi-Fi的浏览器输出模式隔离本机CarPlay启动问题。

独立的Yunmo侧分别出现：16:59:47连接TCP8200超时；16:59:50及17:01:42收到数据但Yunmo校验失败；17:01:14显示模式或尺寸确认超时。校验失败意味着此前已建立到某个8200端点的TCP并收到可解析到校验环节的数据，不意味着Yunmo协商成功，更不能说明JPEG编码失败。日志没有成功的模式/尺寸协商或JPEG发送记录。

对照固定上游YunmoProtocol.kt后，长度和载荷校验求和公式一致；没有原始响应时不能猜测替换校验规则。发现Swift同步查找遗漏上游的command!=FE条件：连续多于4个FE可能被错误当作头。补为与上游一致的8字节滑动窗口；增加独立噪声/额外FE字节测试，原校验拒绝测试继续保留，不绕过校验。该边界是否触发本次失败尚未证实。

新增诊断：实际本机/目标IP和8200端口、TCP建立、请求顺序、收到的命令/载荷长度/首操作码、模式确认与尺寸是否缺失、失败头部及计算/收到的校验值；不记录JPEG画面或Wi-Fi密码。原错误前缀“台铃等待超时/PXC协议”来自复用TailingError，并不意味着路由到台铃/春风输出。30FPS/H264是本机CarPlay输入，625X仪表侧仍为JPEG/目标10FPS，尚无证据表明此处格式配置引发当前失败。
